# Debugging Challenge - Тест на чтение кода и дебаггинг

## Описание задания

Этот тест проверяет способность кандидата:

- **Читать и понимать сложный код** с множественными уровнями абстракции
- **Строить ментальную модель** выполнения программы
- **Отслеживать поток данных** через различные функции и классы
- **Анализировать асинхронные операции** и работу с промисами
- **Выявлять потенциальные проблемы** и баги в коде

## Инструкция для кандидата

Изучите файл `debuggingChallenge.ts` и ответьте на следующие вопросы. **Не запускайте код** - анализируйте его статически, как если бы вы проводили code review.

## Часть 2: Анализ потока выполнения (15 минут)

### Вопрос 2.1

Проследите полный путь выполнения для вызова `processor.processUserData('user-123')`. Перечислите все методы в порядке их вызова.

**Ожидаемый ответ:**

1. `processUserData('user-123')`
2. `checkCache('user-123')` -> возвращает null (первый вызов)
3. `addToQueue('user-123')`
4. `fetchUserData('user-123')` -> `apiClient.getUser('user-123')`
5. `enrichUserData(userData)` -> параллельно:
   - `fetchUserPreferences('user-123')` -> `apiClient.getUserPreferences('user-123')`
   - `fetchUserMetadata('user-123')` -> `apiClient.getUserMetadata('user-123')`
6. `validateAndNormalize(enrichedData)`
7. `saveToCache('user-123', processedData)`
8. `removeFromQueue('user-123')`

### Вопрос 2.2

Что произойдет при повторном вызове `processor.processUserData('user-123')` сразу после первого?

**Ожидаемый ответ:**

- `checkCache` найдет данные в кэше (если TTL не истек)
- Вернет кэшированные данные без API запросов
- Не будет добавления в очередь и последующей обработки

### Вопрос 2.3

Опишите, как работает параллельная обработка в методе `enrichUserData`. Какие операции выполняются параллельно?

**Ожидаемый ответ:**

- Используется `Promise.all` для параллельного выполнения
- Параллельно выполняются: `fetchUserPreferences` и `fetchUserMetadata`
- Основной поток ждет завершения обеих операций перед продолжением

## Часть 3: Анализ асинхронных операций (15 минут)

### Вопрос 3.1

Найдите все места в коде, где используются промисы. Как обрабатываются ошибки в асинхронных операциях?

**Ожидаемый ответ:**

- Все API методы возвращают промисы
- В `processUserData` есть общий try-catch
- В `fetchUserPreferences` и `fetchUserMetadata` есть индивидуальная обработка ошибок
- `Promise.all` в `enrichUserData` может привести к fail-fast поведению

### Вопрос 3.2

Что произойдет, если один из запросов в `Promise.all` завершится с ошибкой?

**Ожидаемый ответ:**

- `Promise.all` немедленно отклонится (fail-fast)
- Ошибка всплывет в `enrichUserData`, затем в основной try-catch
- Пользователь будет удален из очереди, вернется null
- Второй запрос может продолжать выполняться, но его результат будет проигнорирован

### Вопрос 3.3

Проанализируйте использование `delay()`. Зачем нужны эти задержки и как они влияют на производительность?

**Ожидаемый ответ:**

- Имитируют реальные сетевые задержки
- В `fetchUserMetadata` добавляется случайная задержка (0-1000мс)
- Это может привести к race conditions при параллельной обработке
- Влияет на общее время выполнения операции

## Часть 4: Выявление проблем и багов (20 минут)

### Вопрос 4.1 ⚠️ КРИТИЧЕСКИЙ БАГ

В коде есть серьезная проблема с обработкой ошибок в `Promise.all`. Найдите ее и объясните, к чему это может привести.

**Ожидаемый ответ:**

- В `enrichUserData` используется `Promise.all`, но `fetchUserPreferences` и `fetchUserMetadata` имеют собственную обработку ошибок
- Если `fetchUserMetadata` упадет с ошибкой, весь `Promise.all` завершится неудачно
- Это приведет к потере данных пользователя, даже если основные данные и предпочтения получены успешно
- **Решение:** использовать `Promise.allSettled` или обернуть каждый промис в try-catch

### Вопрос 4.2 ⚠️ ПОТЕНЦИАЛЬНАЯ УТЕЧКА ПАМЯТИ

Найдите потенциальную проблему с управлением памятью.

**Ожидаемый ответ:**

- Кэш `Map<string, any>` может расти бесконечно
- Хотя есть TTL, старые записи удаляются только при обращении к ним
- Нет механизма периодической очистки кэша
- **Решение:** добавить периодическую очистку или LRU eviction

### Вопрос 4.3 ⚠️ RACE CONDITION

Есть ли в коде потенциальные race conditions? Где и при каких условиях?

**Ожидаемый ответ:**

- При параллельных вызовах `processUserData` для одного пользователя
- Первый вызов может еще обрабатываться, когда приходит второй
- Очередь предотвращает дублирование, но кэш может быть перезаписан
- Случайные задержки в `fetchUserMetadata` могут привести к непредсказуемому порядку завершения

### Вопрос 4.4 ⚠️ ПРОБЛЕМА С ТИПИЗАЦИЕЙ

Найдите проблемы с типизацией в коде.

**Ожидаемый ответ:**

- `cache = new Map<string, any>()` - слишком широкий тип `any`
- В `fetchUserMetadata` возвращается `any`
- В `ApiResponse` при ошибке `data: null as any` - принудительное приведение типа
- Метаданные не используются в финальном объекте, но получаются
